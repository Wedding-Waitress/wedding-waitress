# Head Table controls and default terminology

The Tables card now uses the same TableGuestList and SortableGuestItem rows for standard and Head Tables. Every real guest, including linked primary participants, has a seat number and ordinary drag handle. Moves out, moves in and reorders update guest assignments and the Head Table order together. Deliberately removed participant reservations are removed; the automatic couple repair has no reservation to recreate. Existing guests retain their seat numbers when someone leaves. Explicit seat positions in head_seating_order preserve gaps across reloads and reception views. The separate arranger remains an explicit centered-layout operation on Save.

Moves read a fresh event-scoped snapshot, validate capacities and reserved positions, and compare old seats/order before writing. A failed multi-request save attempts to restore only this operation's writes; concurrent conflicts are reported instead of overwritten. This uses existing authenticated Data API permissions and needs no new database function or production deployment. Unrelated same-name guests are identified by guest ID and are unchanged when their seats do not shift through an intentional insertion.

The default label uses setup_details.celebrationType: wedding means Bridal Table; engagement, birthday, corporate, school, Christmas, other and unknown categories mean Head Table. It never infers the category from an event title or the seated/cocktail format. Generic legacy default labels are normalized when an owner opens Tables or Guest List; custom labels and ordinary table names remain intact. The stored normalization also keeps shared/raw table consumers consistent.

No customer seating is changed simply by enabling the drag controls. Existing example repairs and the archived Live Streaming flag are preserved.

Drag stability: Head-origin drags retain an invisible source-row placeholder; top and bottom target indicators use overlay space rather than adding height to other cards. Browser measurements changed the neighbouring card height delta from 20px to 0px; source height also stays fixed. Realtime intermediate writes are ignored while the event move is active. Ordinary-table drag presentation is preserved.

Legacy manual events: missing participants are created only through an explicit arranger/create action, using durable event participant IDs reserved before insertion. Automatic reconciliation only links existing eligible reservations and never recreates an intentionally removed participant. Same-name ambiguity requires selection of the actual guest. The specifically authorized legacy wedding was repaired by adding two missing participants to its existing two-seat table and storing its wedding category; a transactional assertion confirmed all 30 existing guest records unchanged.
